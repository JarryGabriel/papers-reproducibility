## The cohort

Four dates, the **same 200 airframes on each**:

| date | role |
|---|---|
| 2025-02-17 | drawn |
| 2025-05-21 | drawn |
| 2025-08-29 | drawn |
| 2025-11-01 | the calibration day the paper was written on |

The three added dates were drawn under seed `20251101`, one working day from each
of three windows spread over the year (2025-02-03..21, 2025-05-12..23,
2025-08-25..29), chosen to avoid school-holiday traffic. Working days only: the
factor of interest is seasonal meteorology, not the weekly traffic cycle — and
traffic volume does not enter the measurement, since the detector works per
flight and register broadcast is a fleet-configuration property.

Fixing the airframes across all four dates is the design. With a different fleet
per date, day and fleet composition are confounded, which is what archived
experiment 11 tried and failed to separate.

## Why the plan is an input and not a product

`flight_plan.csv` is written once and consumed, never regenerated by a script. A
plan rebuilt per run could drift between executions — a different draw, a
different airframe list — and the four dates would stop being comparable. The
draw that produced it is recorded above so it can be checked, not repeated.

## Retrieval

The two CSV files are supplied inputs. Replaying this experiment does not query
or resample an aircraft list. The complete preparation command uses a **new**
destination and copies both inputs there. It downloads and decodes the plan,
then runs identify, preprocess, flag, date-bounded enrich, and clean-speeds.
It never runs derive or segments. The older `01_acquire.py` only acquires data;
it is not the standalone preparation protocol.

From the project root, first install the replay dependencies (see
`src/opensky26_plateau/pipeline/README.md`). Then validate without network access
or output writes:

```bash
python -m opensky26_plateau.pipeline.replay --destination /absolute/new/cohort --dry-run
```

Use a separate, new directory for a real two-aircraft smoke run. This performs
network requests and requires configured OpenSky access:

```bash
python -m opensky26_plateau.pipeline.replay --destination /absolute/new/smoke --smoke 2 --log /absolute/new/smoke/preparation_log.json
```

Omit `--smoke` for the full 200-aircraft plan. Allow roughly 4-5 GB of ERA5
cache per date plus the raw and processed trajectory stores. Each date gets its
own cache; no cache is deleted. The run writes resolved configuration, input
hashes, installed package versions and step outcomes to `replay.json`. Failed
runs remain marked failed. Existing destinations are refused to prevent mixing
cohorts; automatic resume is not implemented.

Measure the prepared store without replacing the versioned results:

```bash
experiment=investigations/reference-availability/experiments/01-bds40-availability
cohort=/absolute/new/cohort
python "$experiment/scripts/04_measure.py" --table "$cohort/flights.delta" --out "$cohort/measurements"
python "$experiment/scripts/05_comm_b_census.py" --raw "$cohort/raw/extended" --out "$cohort/measurements/comm_b_census.json"
python "$experiment/scripts/03_cohort_figures.py" --table "$cohort/flights.delta" --measures "$cohort/measurements" --out "$cohort/figures"
```

Compare these measurements with the versioned outputs. A fresh remote query is
not an attestation of byte-identical historical raw data. Offline orchestration
tests do not establish numerical reproduction of the full cohort.

Experiment 01 reads Delta and raw messages directly; it does not require
`test_flights.parquet`. Exporting that parquet for downstream analyses is a
separate operation, whose required date subset must be chosen by those analyses.
